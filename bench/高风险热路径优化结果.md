# 高风险热路径优化结果

## 测试背景

- 日期：2026-07-06
- 模式：单机单 RouterAgent，本地 UDS 转发
- 拓扑：`client -> gatesvr -> RouterAgent(UDS) -> lobbysvr`
- 本轮目标：尝试 RPC header 生命周期、inflight 复用等更高风险热路径优化。

## 本轮改动

### 1. RPCWireHeader append 编码

新增 `routeragent.AppendRPCWireHeader(dst, h)`，`EncodeRPCWireHeader` 保留原 API，并内部复用 append 编码逻辑。

Wire format 不变。

### 2. RPCWireHeader 零拷贝 string decode

`DecodeRPCWireHeader` 中 `RoutingKey` / `Route` 从 `string([]byte)` 改成 `unsafe.String`，避免每次解码 header 时复制字符串。

这是高风险点，依赖前提是：

- 解码出的 string 生命周期不超过 frame header backing buffer；
- 当前处理链路中 `head.Route` / `head.RoutingKey` 只在 frame 处理期间使用；
- peer pending 场景中 `head` 与 `frame` 一起保存，header backing buffer 仍由 frame 持有。

### 3. inflight 复用尝试后撤回

尝试过用 `sync.Pool` 复用 `rpc.Core` 的 `inflight` 对象。测试通过，但 profile 中出现 `sync.(*poolChain).pushHead` 新分配，并且 QPS 没有提升。

结论：当前 `inflight` 不是足够大的热点，复用收益抵不过 pool 开销和复杂度，因此撤回，保持原来的直接分配。

## 结论

- 本轮高风险优化减少了 `DecodeRPCWireHeader` 的字符串分配，profile 更干净。
- 但 QPS 没有超过上一轮最佳 `345.9k QPS`，实测在 `331k - 342k QPS` 区间。
- `inflight` 复用被验证为不划算，已撤回。
- RouterAgent metrics 仍然干净：`route_miss=0`、`unknown_seq=0`、`late_response=0`、`remote_seq_pending=0`。

## 下一步判断

继续硬压的主要剩余点是：

1. `UDSConn.readLoop` / `ragent.readFrame` 的 buffer 生命周期。
2. `AppendRPCWireHeader` 每次发送仍需分配 owned header。
3. `TCPConn.readLoop` body 分配。

这些都需要引入明确的 buffer ownership / release 协议，否则容易出现 frame 被后续 read 覆盖、异步 callback 读到已复用内存的问题。当前不建议再用零散小改继续推进，应单独设计一套引用计数或 release 机制。
