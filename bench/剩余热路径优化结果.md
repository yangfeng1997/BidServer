# 剩余热路径优化结果

## 测试背景

- 日期：2026-07-06
- 模式：单机单 RouterAgent，本地 UDS 转发
- 拓扑：`client -> gatesvr -> RouterAgent(UDS) -> lobbysvr`
- 本轮目标：继续处理 gate / core 中剩余明确、低风险的热路径分配。

## 本轮改动

### 1. BaseApp 缓存 nodeID uint32

`BaseApp.NodeIDUint32()` 原先每次都会 `nodeid.Parse(app.nodeID)`，内部包含 `strings.Split` 和数字解析。现在在 `NewBaseApp` 时解析一次并缓存，热路径直接返回 `uint32`。

收益：profile 中 `nodeid.Parse` / `strings.Split` 从主要热点中消失。

### 2. TCP / WS 收包通道改为 Packet 值类型

`conn.Connection.Recv()` 从 `chan *codec.Packet` 改成 `chan codec.Packet`。

原先 `TCPConn.readLoop` 每包创建局部 `pkt` 后发送 `&pkt`，会让 packet header 逃逸到堆上。现在直接按值传递 `codec.Packet`，只保留必须的 body 分配。

涉及：

- `internal/core/conn/conn.go`
- `internal/core/acceptor/ws.go`
- `internal/core/dispatcher/gate.go`
- 相关测试 stub

### 3. 保留上一轮 gate TCP 优化

本轮结果包含上一轮已经完成的优化：

- `TCPConn.SendOwned`
- `TCPConn.writeLoop` 复用 `[]byte`
- `codec.EncodeDataMessagePacket`
- gate 回包一次性编码 packet + message
- gate recvLoop 缓存 session，避免每包 `RemoteAddr().String()`

## 结论

- 当前最高达到约 `345.9k QPS`。
- 相比初始长测基线 `296.2k QPS`，最高提升约 `16.8%`。
- 相比上一轮 gate TCP 优化较好结果 `324.4k QPS`，最高提升约 `6.6%`。
- 两轮均 `failed=0`、`reconnects=0`。
- RouterAgent metrics 仍然干净：`route_miss=0`、`unknown_seq=0`、`late_response=0`、`remote_seq_pending=0`。

## 当前剩余热点

最终 gatesvr heap top：

```text
ragent.readFrame                    18.12%
gate.forwardToBackend               13.06%
gate.recvLoop                       11.31%
routeragent.EncodeRPCWireHeader      11.08%
codec.EncodeDataMessagePacket         9.08%
GateDispatcher.HandleSessionPacket    7.08%
TCPConn.readLoop                      7.02%
rpc.Core.OnResponse                   6.89%
rpc.Core.Call                         6.44%
routeragent.DecodeRPCWireHeader       5.47%
TCPConn.writeLoop                     3.18%
```

能继续做的优化已经开始进入更高风险区：

- `TCPConn.readLoop` 的 body 分配本质上是跨 goroutine 生命周期需要，继续降分配需要 buffer pool / 引用计数 / 同步消费模型。
- `ragent.readFrame`、`EncodeRPCWireHeader`、`DecodeRPCWireHeader` 仍有空间，但要么涉及 header 生命周期，要么涉及字符串字段编码与路由逻辑。
- `rpc.Core.Call/OnResponse` 继续优化需要复用 inflight / callback 包装，收益和复杂度需要再评估。

当前建议把这版作为稳定优化点，再单独做下一轮“协议 header / buffer pool”专项。
