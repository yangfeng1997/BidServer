# 集群通信：RouterAgent

RouterAgent 是本框架的集群通信 sidecar。业务进程通过本机 UDS 连接 RouterAgent，跨机器通信由 RouterAgent 之间的 TCP 连接完成。

## 物理拓扑

```text
┌─────────────────────────────────────────────┐
│  物理机 A                                    │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ gatesvr  │  │ lobbysvr │  │  其他进程 │  │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
│       │UDS           │UDS          │UDS      │
│       └──────────────┴─────────────┘        │
│                      │                      │
│              ┌───────▼────────┐             │
│              │  RouterAgent A │◄──── etcd   │
│              └───────┬────────┘             │
└──────────────────────┼──────────────────────┘
                       │ TCP
```

当前实现目录是 `internal/server/routeragent`。默认 UDS 路径为：

```text
/run/routeragent/ra.sock
```

业务进程连接后先发送 Handshake，携带自己的 NodeID。RouterAgent 用 NodeID 区分本机不同业务连接。

## 并发模型

RouterAgent 作为一个 App Module 运行，复用 `internal/core/app` 生命周期：

- `AfterInit` 启动 UDS server、keepalive 和可选 TCP server。
- UDS/TCP read goroutine 收到帧后通过 `app.Poster` 投递到 App 主循环。
- 路由决策、成员表读写、remote seq 映射和广播 waiter 都在主循环任务中处理。
- `WaitReady` 通过 `app.Ready` 等待 UDS/TCP 初始化结果。

当前 App 主循环是事件驱动模型，没有独立 tick 轨道。RouterAgent 的超时类逻辑应使用 `time.AfterFunc` 或 goroutine 回投主循环，避免在 timer goroutine 里直接修改共享状态。

## UDS 帧格式

当前 `frame.go` 使用统一帧格式：

```text
| length(4B, big-endian) | type(1B) | header_len(2B) | header | body |
```

其中：

- `length` 不包含自身 4 字节。
- `header_len` 最大 `uint16`。
- `RpcRequest`、`RpcResponse`、`RpcNotify` 使用 header 承载 RPC 路由头。
- body 是业务 payload 或控制消息 body。

帧类型：

| 值 | 名称 | 说明 |
|---|---|---|
| `0x01` | `Handshake` | 业务进程连接 RouterAgent 后声明 NodeID |
| `0x02` | `HandshakeAck` | RouterAgent 确认注册结果 |
| `0x03` | `RpcRequest` | 服务间请求 |
| `0x04` | `RpcResponse` | 服务间回包 |
| `0x05` | `RpcNotify` | 单向通知 |
| `0x06` | `Heartbeat` | UDS 链路保活 |
| `0x07` | `BroadcastSent` | 广播投递结果通知 |

## RPC Wire Header

当前 `rpc_wire.go` 的头部字段为：

```go
type RPCWireHeader struct {
    SeqID       uint64
    ServerType  uint32
    RoutingMode uint8
    DeadlineMs  int64
    WaiterID    uint64
    FromNodeID  uint32
    ErrCode     uint32
    RoutingKey  string
    Route       string
}
```

RouterAgent 主要读取 `ServerType`、`RoutingMode`、`RoutingKey`、`SeqID`、`FromNodeID` 和 `Route`。业务 payload 不在 RouterAgent 内解析。

字段语义必须保持稳定：`FromNodeID` 始终表示原始调用方节点，用于回包方向和业务上下文传播；`RoutingKey` 在 `RoutingModeDirect` 下表示目标业务 NodeID，用于远端 RouterAgent 投递本地 UDS 连接。跨 RouterAgent 转发时可以把路由改写成 direct target，但不能把 `FromNodeID` 改成目标节点。

## 路由模式

当前 RouterAgent 的路由模式定义在 `resolver.go`：

| 模式 | 说明 |
|---|---|
| `RoutingModeAny` | 从目标 serverType 的节点列表中选择一个节点 |
| `RoutingModeDirect` | 从 `RoutingKey` 解析完整 NodeID，直达该节点 |
| `RoutingModeHash` | 用 `RoutingKey` 对目标 serverType 节点集合取哈希 |
| `RoutingModeBroadcast` | fanout 到目标 serverType 的全部节点 |

当前哈希选择是对按 NodeID 排序后的列表取 FNV hash 余数，不是 ketama 一致性哈希。后续如要减少节点增删扰动，可以替换 `Resolver.PickHash` 实现。

## 本地短路与跨机转发

路由处理流程：

1. 根据 RPC header 选择目标 NodeID 列表。
2. 通过成员表查询目标 NodeID 对应的 RA 地址。
3. 如果目标 RA 地址是本机连接，则直接投递到本地 UDS 连接。
4. 如果目标在其他机器，则通过 `PeerMgr` 获取或建立 TCP peer 连接。
5. 跨机请求分配 remote seq，并在 `RemoteSeqMap` 里记录原始 UDS 连接和原始 seq。
6. 发送到 peer 前保留原始 `FromNodeID`，并把 `RoutingMode/RoutingKey` 改写为 direct target NodeID。
7. 远端 RouterAgent 收到 peer request/notify 后按 `RoutingKey` 找本地 UDS 连接投递；`FromNodeID` 只表示调用方，不用于本地投递。
8. 远端回包返回时再把 remote seq 映射回原始 seq，投递给原始业务进程。

## Peer 连接管理

跨机器转发使用懒连接：只有在目标节点的 `RAAddr` 不是本机，且 `PeerMgr` 中还没有可用连接时，RouterAgent 才会拨号远端 `RAAddr`。

Peer TCP 握手只交换双方 RouterAgent 的 `listenAddr`：

```text
| addr_len(2B, big-endian) | listenAddr |
```

连接建立后，`PeerMgr` 以远端 `listenAddr` 为 key 保存 active link。当前去重策略是“连接替换 + 精确摘除”：

- 第一条握手成功的 incoming / outgoing 连接都会被接受。
- 如果同一个远端 `listenAddr` 已经有 active link，新连接会在 `PeerMgr.Attach` 中替换旧连接。
- 被替换的旧 link 会被主动 `Close`，关闭底层 TCP，避免双连接残留。
- 连接读循环退出时用 `PeerMgr.Detach(addr, link)` 精确摘除；如果该 link 已经被新连接替换，旧连接退出不会误删新连接。

这套语义优先保证连接可收敛：双边同时拨号时允许短暂竞争，但最终 `PeerMgr` 对每个远端 `listenAddr` 只保留一条 active link。

### 发送链路与 pending queue

主路由路径不再在主循环里同步拨号，而是走 `sendPeerOrQueue`：

```text
forwardRPC / sendToNode / legacy route
  -> sendPeerOrQueue(peerAddr, outbound)
      connected + link 可用：非阻塞发送
      未连接 / 连接中：入队 pending
      首个入队者：启动异步 dial
      队列满：request 立即回错，notify 丢弃
dial 成功
  -> Attach active link
  -> flush pending
dial 失败
  -> fail pending
  -> request 立即回 ERR_INTERNAL，不等 RPC timeout
```

关键点：

- `tcpPeerLink.Send` 是非阻塞的，send channel 满时直接返回 `peer send queue full`，不会阻塞 RouterAgent 主循环。
- `dialPeerConn` 使用 `peerDialTimeout = 3s`，TCP 拨号和握手读写都受 deadline 约束。
- 每个 peer 有独立 pending 队列，上限 `peerPendingLimit = 8192`。同腾讯云 VPC、5万 QPS 下覆盖约 160ms 抖动窗口，单 peer 内存约 8MB（1KB payload）。
- 队列满时按消息类型 fail fast：
  - `FrameRpcRequest`：立即回 `RpcResponse`，`ErrCode = ERR_INTERNAL`。
  - `FrameRpcNotify`：丢弃，打错误日志。
  - `FrameRpcResponse`：丢弃，调用方靠 RPC 超时兜底。
- 跨 RA 转发时，发送方只改写 direct target 的 `RoutingKey`，不改写 `FromNodeID`；接收方按 `RoutingKey` 投递本地节点，回包仍依赖原始 `FromNodeID` 和 remote seq 映射返回调用方。
- 发送失败或 dial 失败时，request 一定有反馈，不会只能等超时。

### 状态机

`PeerMgr` 对每个远端 `listenAddr` 维护状态：

```text
Disconnected -> Connecting -> Connected
                       \-> Disconnected（dial 失败）
Connected  -> Disconnected（读/写失败、被替换）
```

只有 `Connected` 且 `Link != nil` 时才直接发送，否则进队列并按需触发异步建连。

### 已具备的工业标准项

- 监听/注册地址配置驱动，不在代码里自动探测公网/内网 IP。
- 首条可用连接不被字典序拒绝，保证可收敛。
- 双连接通过 `Attach` 替换 + 主动关闭旧 TCP 收敛。
- 旧连接退出用 `Detach` 精确摘除，不误删新连接。
- 主循环不阻塞：dial 异步、`Send` 非阻塞。
- 建连期间消息缓存到 bounded pending queue。
- 队列满 fail fast，request 有即时错误反馈。
- 拨号和握手有 deadline。
- etcd 自注册用 CAS，重复 nodeid 启动失败；业务代注册保持覆盖语义。
- 关键节点有日志：dial、handshake、attach、detach、replace、disconnect。

### 锦上添花（非必须，后续可做）

- **重连退避**：当前 dial 失败后靠下次流量触发再 dial，可加指数退避避免对端故障时被频繁触发。
- **pending 水位 metrics**：暴露每个 peer 的 pending 长度，方便监控告警。
- **peer 主动健康检查**：当前靠 read/write 失败被动发现断连，可加主动心跳。
- **连接 generation**：防止旧 dial goroutine 结果覆盖新连接；当前靠 `Attach` 替换已足够，更严谨可加 generation 校验。
- **分级队列**：response 单独队列，避免被 notify/request 挤掉；当前对游戏/集群通信场景够用。

## 服务注册与发现

当前仓库已经有 `etcd_registry.go`，提供：

- `Register(nodeID, raAddr, serverType)`：写入节点信息并用 lease keepalive。
- `Discover(onAdd, onDel)`：全量加载并 watch 节点变化。
- `PeerAddr(nodeID)`：按 NodeID 查询 RA 地址。

RouterAgent 的服务发现由 `EtcdRegistry` 负责，模块装配时应把注册、全量发现和 watch 结果接入 `MemberTable`，并确保所有回调通过 `app.Poster` 回到主循环。

建议 key 语义保持为 NodeID 主键：

```text
/routeragent/nodes/{nodeID}
value: { node_id, server_type, ra_addr, start_at }
```

## Keepalive 语义

`keepalive.go` 只负责 RouterAgent 与本机业务进程之间的 UDS 链路健康。它和客户端心跳不是同一概念：

- RouterAgent keepalive：检测本机业务进程是否仍健康连接 sidecar。
- 客户端 heartbeat：检测玩家客户端连接是否仍存活。

命名和指标上应保持这两个概念分离。
