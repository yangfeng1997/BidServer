要做“商用高并发高吞吐云服务架构”，核心不是把单个 RouterAgent 优化到极限，而是把系统做成：

```text
可水平扩展
可观测
可限流降级
可灰度发布
可自动恢复
数据层不拖垮业务层
容量模型清晰
```

你现在这套 GameServer 已经有了一个不错的起点：`gate + routeragent + lobby + etcd + 配置生成 + 协议生成 + 压测工具`。但要走向商用高并发，需要分阶段补。

**第一阶段：先定义商用目标**

不要先说“越高越好”，要定 SLO：

```text
单区目标：
- 在线连接数：10万？50万？100万？
- 业务 RPC QPS：5万？20万？100万？
- p99 延迟：<50ms？<100ms？
- 单节点最大连接数：1万？5万？
- 单 gate 最大吞吐：多少 Mbps？
- 故障恢复时间：10s？30s？
- 发布是否允许断连？
```

没有这些目标，优化会失焦。

我建议你的第一版目标可以定成：

```text
单 gate: 2万-5万长连接
单 RouterAgent 跨机 RPC: 2万-5万 QPS
单 lobby: 1万-3万业务 QPS
整体通过水平扩展到 10万-50万在线
后台 RPC p99 < 100ms
核心请求 p99 < 50ms
```

这是比较现实的 Go 商用起步目标。

**第二阶段：架构方向**

目标架构应该是这样：

```text
Client
  |
  v
LB / SLB / Ingress
  |
  v
Gate 集群  ---- local UDS ---- RouterAgent 集群边车
  |                              |
  |                              TCP / QUIC / gRPC stream
  v                              |
Lobby / Room / Match / Chat / DBProxy / CacheProxy
  |
Redis / MongoDB / MySQL / MQ
```

核心原则：

```text
gate 负责连接和协议
routeragent 负责服务发现和跨节点路由
业务服负责业务状态
room/battle 类强实时服务尽量做玩家亲和
数据访问走 cache/db proxy 或清晰 DAO 层
所有服务可横向扩容
```

不要让所有东西都变成一个超级中心节点。高并发系统一定要分片。

**第三阶段：你当前项目最应该补的 8 件事**

1. **完整 metrics**

这是商用化第一优先级。

至少要有：

```text
gate:
- 当前连接数
- 每秒收包/发包
- sendCh 水位
- 断连原因
- handler 耗时
- 转发 RPC 耗时

routeragent:
- peer sendCh 水位
- peer pending 水位
- remoteSeq pending
- route miss
- late response
- peer reconnect 次数
- 每个 serverType QPS / p99

lobby:
- 每个 route QPS
- 每个 route p50/p90/p99
- handler 错误码分布
- goroutine 数
- GC pause
```

没有 metrics，高并发优化基本是在猜。

2. **限流和背压**

高并发商用系统一定要能拒绝请求。

要加：

```text
gate 连接数上限
单连接收包速率限制
单 UID 请求速率限制
单 route QPS 限制
RouterAgent peer 队列水位保护
业务 handler 超时保护
```

原则是：**宁可快速失败，也不要无限排队。**

3. **连接和路由分片**

你现在按 `serverType` 建 peer key 是对的。下一步是：

```text
同 serverType 下按 routingKey 分片多连接
同玩家/同房间固定走同一条连接
不同玩家/房间并行
```

比如：

```text
peerKey = peerAddr + ":" + serverType + ":" + shardID
shardID = hash(routingKey) % N
```

这样可以突破单 `serverType` 单 TCP 写循环瓶颈。

4. **业务亲和**

游戏云服务要避免每个请求都跨机乱跳。

常见做法：

```text
玩家登录后绑定 gate
玩家分配到 lobby/room shard
gate 记录 uid -> backend node
同玩家请求直达同一业务节点
房间内玩家固定到同一个 room 节点
```

你现在已经有 `BoundNodes`，这个方向是对的，要继续强化。

5. **热路径降日志**

商用高吞吐下，热路径不要打 info。

比如 ping/pong、每帧转发、每次 route 成功，不应默认 info。

应该改成：

```text
错误日志：采样
慢请求日志：超过阈值才打
关键事件：连接建立/断开/注册/发现
性能数据：metrics，不靠日志
```

6. **部署上云**

要走商用云服务，最终建议上 Kubernetes 或至少容器化。

需要补：

```text
Dockerfile
docker-compose 本地集群
K8s Deployment / StatefulSet
ConfigMap / Secret
Service / Headless Service
readinessProbe
livenessProbe
Prometheus metrics endpoint
优雅停服 preStop
滚动发布策略
```

RouterAgent 这种 sidecar 模型很适合 K8s，但要设计好：

```text
每个 Pod 一个业务进程 + 一个 RouterAgent
或者每台 Node 一个 RouterAgent DaemonSet
```

你现在更像“sidecar per host/process group”，后面可以演进。

7. **数据层架构**

高并发最终经常死在 Redis / DB，不死在网络。

要明确：

```text
Redis Cluster 封装
MongoDB/MySQL DAO 层
缓存穿透/击穿/雪崩保护
写入合并
异步落库
脏标记
WAL 或可靠队列
分库分表策略
```

游戏业务里，玩家数据通常不能每个请求都直接打 DB。要做：

```text
登录加载
内存态修改
定时/事件落盘
下线落盘
异常恢复
```

8. **压测体系**

压测不能只靠 `client_sim` 手动跑。

要有：

```text
固定压测场景
固定数据记录格式
自动生成报告
不同 clients 梯度
不同 payload 大小
单机/跨机/多机对比
失败类型分类
服务端 metrics 同步采集
```

否则每次优化都很难判断是真的变快，还是环境波动。

**建议路线图**

我建议按这个顺序做：


当前跨机压测大概是：

```text
跨机 RA 链路：18k QPS 左右
500 clients:  p50 26ms, p99 54ms
1000 clients: p50 52ms, p99 101ms
```

所以现状是：

```text
p99 < 100ms：接近达标，但 1000 clients 已经擦边
核心请求 p99 < 50ms：500 clients 接近，1000 clients 不达标
跨机 5W QPS：当前还差约 2.5-3 倍
```

**还有哪些优化空间**

1. **先补可观测性，这是第一优先级**

现在还不知道 18k QPS 的瓶颈到底在哪里。可能是：

```text
RA1 peer TCP sendCh 堆积
RA1 remoteSeq pending 堆积
RA2 UDS 到 lobby 堆积
lobby 主循环堆积
gate 回客户端 sendCh 堆积
日志 IO
GC
client_sim 自身瓶颈
```

所以第一步不是直接改网络，而是补：

```text
peer sendCh 水位
UDS sendCh 水位
pending 队列水位
remoteSeq pending
incomingPeerSeq 数量
每个 route QPS / p99
每个 serverType QPS / p99
gate 当前连接数
gate 收发包速率
lobby handler 耗时
pprof
GC pause
```

没有这些，后面优化是在猜。

2. **热路径日志降级**

商用高吞吐下，热路径不能打 info。

这类日志要降到 debug 或采样：

```text
每次 ping/pong
每次转发成功
每次 route 成功
每帧收发
高频队列状态
```

保留：

```text
连接建立/断开
注册/注销
peer reconnect
route miss
queue full
慢请求
错误码异常
```

而且错误日志也要采样。日志 IO 对 p99 的杀伤很大。

3. **RouterAgent 单 serverType 多连接分片**

你现在已经按：

```text
peerAddr:serverType
```

隔离连接，这是正确的。

但你的目标是跨机 5W QPS。单个 `serverType` 如果只有一条 TCP 写循环，迟早会碰到单 goroutine、单连接写端瓶颈。

下一步可以做：

```text
peerKey = peerAddr + ":" + serverType + ":" + shardID
shardID = hash(routingKey) % N
```

要求：

```text
同玩家 / 同房间 / 同 routingKey 固定走同一条连接
不同玩家 / 不同房间分散到多条连接
```

这样既能保序，又能并行。

例如：

```text
ST_LOBBY: 4 条连接
ST_ROOM:  8 条连接
ST_CHAT:  2 条连接
```

这是从 18k 冲 5W QPS 最关键的优化之一。

4. **响应优先队列**

现在请求、响应、notify 可能共用队列。高压下更合理的是：

```text
高优先级：Response / Heartbeat / Control
中优先级：Request
低优先级：Notify / Broadcast
```

响应优先能更快释放 caller 的 pending waiter，降低：

```text
remoteSeq pending
调用方 timeout
p99 延迟
```

对核心请求 p99 < 50ms 很有帮助。

5. **背压和快速失败**

商用系统不能无限排队。

要加水位策略：

```text
peer sendCh > 70%：告警/采样日志
peer sendCh > 90%：非核心请求快速失败
pending > 阈值：拒绝新请求
route 超时剩余时间不足：直接失败，不再排队
```

原则是：

```text
宁可快速失败，也不要排队 500ms 后再失败。
```

这对 p99 非常重要。

6. **gate 连接层优化**

单 gate 5W 连接是可以做的，但要注意 Go 模型下的成本。

当前如果是：

```text
每连接 read goroutine
每连接 write goroutine
每连接 sendCh
```

5W 连接就是 10W goroutine 级别。这不是不能跑，但要严格控制：

```text
goroutine 栈内存
sendCh 大小
空闲连接心跳
写队列水位
慢客户端踢出
```

5W 连接下，sendCh 如果每个都 4096，内存风险很大。客户端连接队列不能像服务间 peer 那样无脑放大。

gate 应该区分：

```text
客户端连接 sendCh 小一些
服务间 peer sendCh 大一些
```

客户端慢连接要踢，不能堆。

7. **业务服务分片和亲和**

你已经明确业务服务后面会分片，这是对的。

要把 routingKey 设计好：

```text
uid -> lobby shard
roomID -> room shard
guildID -> guild shard
matchPool -> match shard
```

gate 要尽量记住绑定关系：

```text
uid -> backend node
session -> bound nodes
```

这样核心请求不需要每次重新 hash，也不容易跨机乱跳。

8. **序列化和 buffer 优化**

现在协议栈里会有不少 `make/copy`：

```text
EncodeFrame
DecodeFrame
EncodePacket
DecodePacket
proto marshal/unmarshal
```

后面可以做：

```text
sync.Pool 复用 buffer
限制最大包体
减少 DecodeFrame 的重复 copy
批量写使用 net.Buffers/writev
大 payload 走引用或池化
```

这类优化通常不是第一刀，但在冲 5W-10W QPS 时会变重要。

9. **压测工具要升级**

现在 `client_sim` 还偏手工工具。要做商用目标，需要：

```text
矩阵压测
JSON/CSV 输出
自动对比上一轮
错误后重连
不同 payload 大小
不同 route 混合比例
长连接空闲 + 少量活跃模型
服务端 metrics 同步采集
```

真实 50W 在线不是 50W 个连接都疯狂发请求。压测模型要包含：

```text
90% 空闲连接
9% 低频活跃
1% 高频活跃
少量异常客户端
```

否则数据会误导容量规划。

我建议目标拆成三档：

```text
跨机 18k QPS，p99 50-100ms

```
