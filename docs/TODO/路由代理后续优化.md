# 路由代理后续优化

本文记录 RouterAgent 路由系统当前已完成状态，以及后续从“可用且正确”走向“高压稳定、可观测、可灰度演进”的待办项。

## 当前状态

当前 RouterAgent 路由协议与核心链路已经形成完整闭环：

- 请求与响应都使用明确的 `SrcNodeID` / `DestNodeID` 端点语义。
- 本机 UDS 与跨机 RouterAgent TCP 使用同一套 RPC envelope。
- 跨机请求通过 `RemoteSeqMap` 映射远端 seq，回包时能还原调用方原始 seq。
- peer 回包优先复用原请求进入的 peer 连接，避免不必要的反连。
- peer 连接按 `serverType` 建 key，不同服务类型之间流量隔离。
- peer 发送非阻塞，连接建立期间有 pending 队列，失败时能给调用方返回错误。
- incoming peer 已启动读写循环，能完整承载请求与响应双向流量。
- incoming peer 请求 seq 已有超时清理和断连清理，避免长期堆积。
- `RemoteSeqPending` 由 `RemoteSeqMap` 维护，避免外层路由逻辑误加减。
- `MemberTable.ListByServerType` 返回快照，避免 resolver 排序污染内部状态。
- 当前全量测试 `go test ./...` 已通过。

结论：当前系统已经过了“能不能通”的阶段，核心正确性缺口基本补齐。后续重点应放在高并发稳定性、可观测性、故障治理和协议灰度能力。

## P0 可观测性补强

### sendCh 水位指标

为 RouterAgent peer TCP、UDS、本地 ragent client 的发送队列增加水位指标：

- 当前长度。
- 历史最大长度。
- 队列满次数。
- 按 `peerKey` / `serverType` 维度拆分。

价值：压测失败时能判断是写端拥塞、对端慢、还是应用层处理慢。

### pending 队列水位

为 peer pending 队列增加指标：

- `pending[peerKey]` 当前长度。
- 入队次数。
- 溢出次数。
- 等待最长时间。

价值：能区分“正在建连的正常排队”和“对端长期不可达导致堆积”。

### seq 与路由异常指标分维度

现有 `route_miss`、`late_response`、`remote_seq_pending` 等指标后续应增加维度：

- `peerKey`
- `serverType`
- `route`
- `srcNodeID`
- `destNodeID`

价值：避免只有全局计数，无法定位具体哪个服务类型或节点异常。

## P1 压测工具修正

### client_robot 错误后重连

`tools/client_robot` 当前每个客户端复用一条 TCP 连接连续发请求。如果一次 read timeout、seq mismatch、cmd mismatch 或 payload mismatch 后继续复用连接，迟到响应可能污染下一次读取，导致失败分类失真。

待办：

- `read` 超时后关闭连接并重连。
- `seq_mismatch` 后关闭连接并重连。
- `cmd_mismatch` / `payload_mismatch` 后关闭连接并重连。
- 汇总中单独统计 reconnect 次数。

价值：让压测结果更接近真实服务端表现，减少客户端连接流被污染带来的噪声。

## P1 背压与保护策略

### 慢 peer 快速失败

当某个 peer 的 sendCh 或 pending 队列超过水位时，不应无限排队。后续可增加策略：

- 超过软水位时日志采样告警。
- 超过硬水位时直接返回 `ERR_TIMEOUT` 或 `ERR_INTERNAL`。
- 对单个 `peerKey` 熔断，避免拖垮其他 `serverType`。

价值：避免慢对端引起整体内存上涨和延迟扩散。

### 响应帧优先级

当前请求、响应、通知共用发送队列。后续可考虑：

- 响应帧优先发送。
- 心跳和控制帧优先发送。
- 普通 notify 可低优先级。

价值：高压下优先释放调用方 waiter，降低超时和 `remoteSeq` 堆积。

### 日志采样

高并发路径上的队列满、路由失败、迟到响应等日志应采样：

- 相同 `peerKey` / `route` 每秒最多 N 条。
- 统计值走 metrics，日志只保留摘要。

价值：避免故障时日志 IO 反向放大延迟。

## P2 协议灰度能力

### wire header version

当前 RPC wire header 新旧进程不能混跑。后续可在 header 或 frame handshake 中加入版本号：

- peer 握手时声明 wire version。
- 版本不兼容时启动或建连阶段直接拒绝。
- 日志明确输出本端版本和对端版本。

价值：发布时避免 decode 失败表现成路由异常。

### peer handshake magic

peer handshake 当前依赖长度和字段顺序。后续可增加 magic：

- 固定 magic 标识 RouterAgent peer 协议。
- 防止误连到其他 TCP 服务时产生难懂错误。

价值：提升排障体验和协议健壮性。

## P2 连接生命周期治理

### reconnect backoff + jitter

当前 peer 连接失败后由后续请求触发重连。后续可增加退避策略：

- 指数退避。
- 随机 jitter。
- 最大退避上限。
- 成功后重置退避。

价值：避免对端重启或网络抖动时大量 RA 同时重连。

### 连接 generation

为 peer link 增加 generation：

- Attach 时生成递增 generation。
- readLoop / writeLoop / detach 时带 generation 校验。
- 旧连接迟到事件不能影响新连接状态。

价值：进一步降低旧连接关闭、迟到回调与新连接替换之间的竞态风险。

### 主动健康检查

基于 peer heartbeat 或轻量 ping 增加主动健康检查：

- 连续 N 次失败标记 peer unhealthy。
- unhealthy 状态下快速失败或触发重连。
- metrics 暴露健康状态。

价值：比等业务请求超时更早发现链路问题。

## P3 性能继续扩展

### 按 serverType 的连接池深化

当前已经按 `peerAddr:serverType` 建连接，隔离不同服务类型。后续如单个 `serverType` 仍有极高 QPS，可继续演进：

- 单 `serverType` 下多连接。
- 按 route 或 routing key 做连接亲和。
- 保证同一玩家或同一 routing key 固定走同一连接。

价值：突破单 `serverType` 单 TCP 写端 goroutine 的吞吐上限。

注意：不同 `serverType` 之间本来就不要求保序；真正需要保证的是同一 `serverType` 内、同一玩家或同一 routing key 的消息顺序。

### batch 写策略调优

当前 drain-batch 已降低 syscall 密度。后续可继续调优：

- batch size 配置化。
- 增加最大等待时间窗口。
- 按帧类型选择不同 batch 策略。
- 响应帧低延迟，notify 帧高吞吐。

价值：在 QPS、p99 延迟和 CPU 消耗之间找到更稳的平衡点。

## P3 工程化补充

### 运维命令安全化

压测和部署文档应继续避免默认使用全局 `stopall.sh` / `startall.sh`，优先提供精确进程控制命令。

价值：避免共享测试环境中误停其他任务。

### 敏感凭据处理

文档和脚本不要把 GitHub token、SSH 密码、Redis 密码写入命令行、URL、日志或提交记录。

价值：避免凭据进入 shell history、进程列表、日志和 git 历史。
