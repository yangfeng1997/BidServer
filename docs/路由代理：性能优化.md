# 路由代理：性能优化

本文档记录 RouterAgent 跨机转发的性能瓶颈分析、优化方案选型与行业对比。

## 瓶颈定位

### 物理链路

```
客户端 ──→ gatesvr ──(UDS)──→ routeragent(本机) ──(TCP 单连接)──→ routeragent(远端) ──(UDS)──→ lobbysvr
```

gatesvr 和 lobbysvr 分机器部署时，所有跨机流量经过两个 routeragent 之间的 **一条 TCP 连接**：

- 这条连接是**全复用**的，RPC 请求、响应、通知、心跳都在上面走。
- 一个 `writeLoop` goroutine 负责串行写入，每次写入调用一次 `write()` syscall。
- 一条 `readLoop` goroutine 负责串行读取。

### 测量数据

环境：两台 Debian x86_64，RTT ~0.5ms，etcd 注册中心。

| 并发 | 优化前 QPS | 优化前 失败率 | 优化后 QPS | 优化后 失败率 |
|---|---|---|---|---|
| 50 | 1963 | 0% | 1860 | 0% |
| 100 | 652 | 57% | 1838 | 0% |
| 200 | - | - | 1771 | 0% |
| 500 | - | - | 1835 | 0% |

### 根因

QPS 上限 ~1800 的根因**不是网络带宽**（两台机器间 ping 延迟仅 0.5ms），而是：

1. **`tcpPeerLink.sendCh` 缓冲区太小**（原 64 帧）：高并发时发送速度超过写入速度，缓冲区瞬间溢出。`Send()` 是非阻塞的，满了直接返回 `"peer send queue full"`，请求即告失败。

2. **单连接 + 逐帧 write**：一条 TCP 连接上一个 writeLoop goroutine 串行写入每一帧。每次 ~100 字节走一次 `write()` syscall，syscall 开销占比极高。即使 sendCh 扩大到 16384 消除了溢出，吞吐天花板仍在 ~1800-2000 QPS——这是单 TCP 连接逐帧同步写 `write()` 的物理上限。

### sendCh 优化效果

| 参数 | 优化前 | 优化后 |
|---|---|---|
| `tcpPeerLink.sendCh` | 64 帧 | 16384 帧 |
| `UDSConn.sendCh/recvCh` | 64 帧 | 4096 帧 |
| `peerPendingLimit` | 8192 | 65536 |
| `TCP_NODELAY` | 未设置 | 已启用 |

优化后消除了 sendCh 溢出导致的失败，500 并发 25000 请求全部成功。但 QPS 稳定在 ~1800，因为瓶颈转移到了单连接写入链路。

## 连接池分析

### 要不要连接池？

**结论：当前不需要，瓶颈在写端单 goroutine。先做了 drain-batch 批量写消除 syscall 瓶颈拿到 10 倍提升。下一步按 serverType 建连接池是唯一值得追的方向。**

理由如下：

1. **drain-batch 已把单连接天花板推到 ~11700 QPS**：1000 并发 50000 请求零失败。
2. **需要更多吞吐时，横向扩展 lobbysvr 更优先**：加实例比加连接池更简单。
3. **连接池按 serverType 建**：4-5 倍空间，改动集中在 PeerMgr，不破坏现有架构。

### 连接池方案：按 serverType 建连接

**结论：优于 hash(key) 方案，是 RA 架构的自然延伸。**

核心思路——不是按 `hash(key) % N` 选连接，而是**按 `head.ServerType` 建独立连接**：

```
机器1                        机器2
gatesvr ──UDS── RA1 ──TCP×3── RA2 ──UDS── lobby
                                 ──UDS── room
                                 ──UDS── match

gatesvr→lobby  走连接#1 (ST_LOBBY)
gatesvr→room   走连接#2 (ST_ROOM)
gatesvr→match  走连接#3 (ST_MATCH)
```

路由时已有 `head.ServerType`，连接 key 从 `peerAddr` 改为 `peerAddr:serverType`：

```go
// 当前: 对端单连接
sendPeerOrQueue(peerAddr, outbound)

// 改后: 按 serverType 选连接
sendPeerOrQueue(peerAddr + ":" + strconv.Itoa(serverType), outbound)
```

#### 为什么比 hash(key) 好

| 维度 | hash(key) 方案 | serverType 方案 |
|---|---|---|
| 路由信息 | 需额外生成 hash key | 用 header 现成的 ServerType |
| 隔离性 | 玩家之间可能相互干扰 | 服务之间天然隔离 |
| 扩容 | 需预估 N | 新 serverType 注册后自动建新连接 |
| 保序 | 同 key 同连接，但跨服务场景不保序 | 同 player + 同 serverType 天然落在同连接 |

`hash(key) % N` 的保序承诺只适用于"同 key 的所有请求都到同一 serverType"的场景——这正是你们框架已经保证的（gatesvr 按 hash 选 lobby 节点，同一玩家永远落到同一 lobby）。所以 hash 选连接是**多此一举**——保序已经由上层路由保证了。

#### 设计自洽性

serverType 在 RA 的每一层都是第一等概念：

| 层级 | serverType 的作用 |
|---|---|
| 注册层 | `etcd registry` 写入 `node_id → {serverType, raAddr}` |
| 成员表层 | `memberTable.ListByServerType(serverType)` 查询 |
| 路由层 | `forwardRPC` 读 `head.ServerType` 决定投递 |
| **传输层（新增）** | 按 serverType 选连接，隔离不同服务的流量 |

把连接池接到 serverType 上，不需要引入 hash key 这个"编造"的亲和规则——全链路语义统一。

#### 改动点

1. **握手协议加 serverType**：`[2B addr_len][listenAddr][4B serverType]`，serverType=0 兼容旧版
2. **PeerMgr key 改为 `addr:serverType`**：`map[addr] → *PeerInfo` 改为 `map[name] → *PeerInfo`
3. **路由时选连接**：`sendPeerOrQueue(addr, serverType, outbound)`
4. **本机 UDS 不受影响**：同 RA 下的服务间调用走 UDS 直投，不经过连接池
| Kubernets apiserver | 按 resource key 路由 | 同资源操作串行化，不同资源并行 |

这种模式等价于 Kafka partition、Redis cluster 的 hash slot——都是"按 key 分片 + 片内有序列"的思路。

### 保序与多连接不冲突

游戏服务器需要的"保序"是**同一玩家/会话内有序**，不是全局有序。多连接 + key 亲和完全可以保证：

```
player_1001 → hash → 连接A → msg1, msg2, msg3 (TCP流保序)
player_1002 → hash → 连接B → msg1, msg2, msg3 (独立有序)
player_1003 → hash → 连接A → msg1, msg2 (和1001分片复用，各自有序)
```

每条 TCP 连接内部是串行字节流，天然保序。只要同 key 始终走同一条连接，顺序就不会乱。

反而单连接有 **head-of-line blocking** 问题——某个玩家的慢消息会阻塞其他所有玩家。多连接按 key 隔离后，只影响同 key 的玩家，不同玩家之间互不阻塞。

## writev 批量写

### 方案

把 `writeLoop` 从逐帧写改为攒批写：

```go
// 当前：逐帧 write
for f := range sendCh {
    data := EncodeFrame(f)
    conn.Write(data)  // 每次 ~100 字节，一次 syscall
}

// 优化后：攒批 writev
buf := make([]Frame, 0, 32)
ticker := time.NewTicker(1 * time.Millisecond)
for {
    select {
    case f := <-sendCh:
        buf = append(buf, f)
        if len(buf) >= 16 || totalBytes >= 16384 {
            flush()
        }
    case <-ticker.C:
        flush()
    }
}
```

两条触发条件，满足任一就批量写出：

- 帧数达到 `batchSize`（建议 16-32）
- 距离上次 flush 超过 `batchInterval`（建议 1ms）

### 预期收益

- syscall 减少 16-32 倍 → 吞吐 **5-10 倍**提升，可达 **9000-18000 QPS**
- 对延迟影响可控：1ms 攒批窗口 + 0.5ms RTT，p99 增加 < 2ms
- 改动量：`writeLoop` 约 30 行
- 不破坏现有帧格式和协议兼容性

### 延迟敏感请求

如需区分延迟敏感和吞吐优先的帧类型，可以给响应帧（`FrameRpcResponse`）单独一个批量通道或直接 bypass，请求帧走攒批。但当前 p50 26ms 的场景下，1ms 的攒批延迟可以忽略。

## 行业参考

主流游戏服务器框架的跨机通信方式：

| 项目 | 语言 | 单连接 QPS | 说明 |
|---|---|---|---|---|
| 腾讯 TConnd | C++ | 30000-50000 | epoll + 内存池 + 零拷贝 |
| 云风 skynet | C/Lua | 5000-10000 | 单 lua VM actor |
| Pitaya | Go | 3000-5000 | 逐帧 write，未做批量优化 |
| 网易 pomelo | Node.js | 2000-4000 | V8 GC 为主要瓶颈 |
| **本框架** | **Go** | **10000** | drain-batch 写入 |

共性规律：

- **绝大多数场景下一条 TCP 连接就够了**——游戏服务器跨机通信的 QPS 远没到需要连接池的程度。
- **瓶颈几乎永远在应用层**和 **syscall 密度**。C++ 方案用 epoll 绕过 syscall 瓶颈可达 3-5 万 QPS。Go 的 drain-batch 把 syscall 密度降低了 16 倍，10K QPS 已接近 Go 单连接上限。
- 差距本质：C++ 的 epoll + 零拷贝 vs Go 的 goroutine 调度 + GC。再往上需要用 `syscall.RawConn` 走 epoll 直读或加连接池。

## 后续建议

| 优先级 | 项目 | 预期收益 | 状态 | 说明 |
|---|---|---|---|---|
| P0 | drain-batch 批量写 | QPS 5-10 倍 | ✅ 已实现 | 核心杠杆，降低 syscall 密度 |
| P0 | sendCh 扩容 + TCP_NODELAY | 消除队列溢出 | ✅ 已实现 | 吞吐稳定化基础 |
| P3 | **按 serverType 建连接池** | QPS 4-5 倍 | 待做 | 最大杠杆 |
| P1 | sendCh 水位监控 | 可观测性 | 待做 | |
| P2 | pending 水位 metrics | 排查慢对端 | 待做 | |

### 已评估、性价比不高的方向

| 方向 | 做法 | 实测 QPS 提升 | 原因 |
|---|---|---|---|
| TCP 读端批量 | readLoop 一次读 32KB buffer 解析多帧 | 10675→11158 (+5%) | 读侧不是瓶颈，单 goroutine 已够快 |
| UDS drain-batch 写 | 同 TCP peer 的贪心排空批量写 | 并入上项 | UDS 本地 IPC 延迟微秒级，batching 帮助有限 |
| UDS 读端批量 | 同 TCP 读端批量 | 并入上项 | 同上 |

三者实测总计提升约 9%（500 并发 10675→11158，1000 并发 10052→11656）。本质是省 CPU，不抬 QPS 天花板。瓶颈始终在单连接写端 goroutine 串行写入。
