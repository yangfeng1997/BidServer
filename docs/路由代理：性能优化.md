# 路由代理：性能优化

本文档记录 RouterAgent 跨机转发的性能瓶颈分析、优化方案选型与行业对比。

## 瓶颈定位

### 物理链路

```
客户端 ──→ gatesvr ──(UDS)──→ routeragent(本机) ──(TCP 单连接)──→ routeragent(远端) ──(UDS)──→ lobbysvr
```

gatesvr 和 lobbysvr 分机器部署时，所有跨机流量经过两个 routeragent 之间的 **一条 TCP 连接**：

- 这条连接是**全复用**的，RPC 请求、响应、通知、心跳都在上面走。
- 一个 `writeLoop` goroutine 负责串行写入，每次写入调用一次 `write()` syscall。
- 一条 `readLoop` goroutine 负责串行读取。

### 测量数据

环境：两台 Debian x86_64，RTT ~0.5ms，etcd 注册中心。

| 并发 | 优化前 QPS | 优化前 失败率 | 优化后 QPS | 优化后 失败率 |
|---|---|---|---|---|
| 50 | 1963 | 0% | 1860 | 0% |
| 100 | 652 | 57% | 1838 | 0% |
| 200 | - | - | 1771 | 0% |
| 500 | - | - | 1835 | 0% |

### 根因

QPS 上限 ~1800 的根因**不是网络带宽**（两台机器间 ping 延迟仅 0.5ms），而是：

1. **`tcpPeerLink.sendCh` 缓冲区太小**（原 64 帧）：高并发时发送速度超过写入速度，缓冲区瞬间溢出。`Send()` 是非阻塞的，满了直接返回 `"peer send queue full"`，请求即告失败。

2. **单连接 + 逐帧 write**：一条 TCP 连接上一个 writeLoop goroutine 串行写入每一帧。每次 ~100 字节走一次 `write()` syscall，syscall 开销占比极高。即使 sendCh 扩大到 16384 消除了溢出，吞吐天花板仍在 ~1800-2000 QPS——这是单 TCP 连接逐帧同步写 `write()` 的物理上限。

### sendCh 优化效果

| 参数 | 优化前 | 优化后 |
|---|---|---|
| `tcpPeerLink.sendCh` | 64 帧 | 16384 帧 |
| `UDSConn.sendCh/recvCh` | 64 帧 | 4096 帧 |
| `peerPendingLimit` | 8192 | 65536 |
| `TCP_NODELAY` | 未设置 | 已启用 |

优化后消除了 sendCh 溢出导致的失败，500 并发 25000 请求全部成功。但 QPS 稳定在 ~1800，因为瓶颈转移到了单连接写入链路。

## 连接池分析

### 要不要连接池？

**结论：当前场景下不需要，建议先做 writev 批量写。**

理由如下：

1. **QPS 瓶颈在"逐帧 write"，不在"连接数"**：单连接 `writeLoop` 每次只写一帧就 syscall，这是吞吐的根因。加 4 条连接、每条仍是逐帧写，总吞吐能到 ~7200，不如一条连接 writev 批量写到 10000+。

2. **保序多此一举**：你们框架已有 `RoutingKey` 和 `Hash` 路由模式。同一玩家的消息天然走同一个 lobbysvr 节点（hash 到同一台机器），不存在跨连接乱序问题。不同玩家的消息本来就不需要保序。

3. **连接数够用**：即便是 10 台机器全互联，对端也只有 9 个 TCP peer。36 个连接（每对 4 条）对 Linux 完全不算事。100 台机器才需要考虑分层。

4. **后续加连接池很简单**：`PeerMgr` 当前是 `map[addr] → *PeerInfo`（单 link），改为 `map[addr] → []*tcpPeerLink`（link 池），按 `RoutingKey` hash 选连接即可。不破坏现有架构。

### 如果要做连接池

```
player_id=1001 ──→ hash(1001) % 4 = 1 ──→ 连接#1
player_id=1002 ──→ hash(1002) % 4 = 3 ──→ 连接#3
player_id=1003 ──→ hash(1003) % 4 = 1 ──→ 连接#1  ← 和 1001 同连接, 有序
```

同 RoutingKey 的消息 hash 到同一条连接，保证同一玩家消息有序。同一条连接上的不同玩家之间自然并发，互不阻塞。

这种模式等价于 Kafka partition、Redis cluster hash slot 的分片思路——都是"按 key 分片 + 片内有序"。

行业中使用连接池 + key 亲和方案的案例：

| 项目 | 分片策略 | 做法 |
|---|---|---|
| Kafka | `hash(key) % partition` | 同 key 消息走同一 partition，partition 内有序 |
| Redis Cluster | CRC16(key) % 16384 | 固定 16384 个 hash slot，按 slot 路由到节点 |
| 腾讯 Leaf/GoFrame | `hash(key) % N` | 连接池按业务 key 分片，同 key 走同连接 |
| Kubernets apiserver | 按 resource key 路由 | 同资源操作串行化，不同资源并行

这种模式等价于 Kafka partition、Redis cluster 的 hash slot——都是"按 key 分片 + 片内有序列"的思路。

## writev 批量写

### 方案

把 `writeLoop` 从逐帧写改为攒批写：

```go
// 当前：逐帧 write
for f := range sendCh {
    data := EncodeFrame(f)
    conn.Write(data)  // 每次 ~100 字节，一次 syscall
}

// 优化后：攒批 writev
buf := make([]Frame, 0, 32)
ticker := time.NewTicker(1 * time.Millisecond)
for {
    select {
    case f := <-sendCh:
        buf = append(buf, f)
        if len(buf) >= 16 || totalBytes >= 16384 {
            flush()
        }
    case <-ticker.C:
        flush()
    }
}
```

两条触发条件，满足任一就批量写出：

- 帧数达到 `batchSize`（建议 16-32）
- 距离上次 flush 超过 `batchInterval`（建议 1ms）

### 预期收益

- syscall 减少 16-32 倍 → 吞吐 **5-10 倍**提升，可达 **9000-18000 QPS**
- 对延迟影响可控：1ms 攒批窗口 + 0.5ms RTT，p99 增加 < 2ms
- 改动量：`writeLoop` 约 30 行
- 不破坏现有帧格式和协议兼容性

### 延迟敏感请求

如需区分延迟敏感和吞吐优先的帧类型，可以给响应帧（`FrameRpcResponse`）单独一个批量通道或直接 bypass，请求帧走攒批。但当前 p50 26ms 的场景下，1ms 的攒批延迟可以忽略。

## 行业参考

主流游戏服务器框架的跨机通信方式：

| 项目 | 语言 | 单连接 QPS | 说明 |
|---|---|---|---|---|
| 腾讯 TConnd | C++ | 30000-50000 | epoll + 内存池 + 零拷贝 |
| 云风 skynet | C/Lua | 5000-10000 | 单 lua VM actor |
| Pitaya | Go | 3000-5000 | 逐帧 write，未做批量优化 |
| 网易 pomelo | Node.js | 2000-4000 | V8 GC 为主要瓶颈 |
| **本框架** | **Go** | **10000** | drain-batch 写入 |

共性规律：

- **绝大多数场景下一条 TCP 连接就够了**——游戏服务器跨机通信的 QPS 远没到需要连接池的程度。
- **瓶颈几乎永远在应用层**和 **syscall 密度**。C++ 方案用 epoll 绕过 syscall 瓶颈可达 3-5 万 QPS。Go 的 drain-batch 把 syscall 密度降低了 16 倍，10K QPS 已接近 Go 单连接上限。
- 差距本质：C++ 的 epoll + 零拷贝 vs Go 的 goroutine 调度 + GC。再往上需要用 `syscall.RawConn` 走 epoll 直读或加连接池。
